## 1. 배경

그룹 분리(`separateLabelGroup`)와 원복(`mergeSplitGroupToLot`)은 여러 행에 대한 **순차 `update` 다단계**로 구현되어 있다. **트랜잭션이 없다.**

```
[분리]
 ① 남은 번지 그룹 재승격          ← update N건
 ② 분리 대상에 group_key + 대표 지정  ← update M건
 ③ 이동 멤버 detached_visible = false ← update M건
```

Ver_1.0은 이 문제를 **실행 순서 설계**로 완화했다.
①을 ②보다 먼저 수행하므로, ②에서 실패해도 잔여 SUB가 이탈한 대표를 가리키는 **dangling parent는 발생하지 않는다**(BR-G05-c). 최악의 경우 중복 대표가 남고 다음 재정렬에서 자가 치유된다.

그러나 이는 **피해 축소이지 근본 해결이 아니다.**

> PRD §5.3: "현재 그룹 조작은 순차 `update` 다단계이며 **트랜잭션 원자성이 없다.** NFR-11~13은 앱 로직 방어에 의존하며, RPC 원자화는 Ver_1.1 과제다."

## 2. 문제

| # | 문제 |
| --- | --- |
| 1 | 네트워크 단절·탭 종료·권한 오류가 **중간 단계에서** 발생하면 그룹이 중간 상태로 남는다 |
| 2 | 중복 대표 상태에서는 "그룹당 대표 1개"(NFR-11)가 일시적으로 깨진다 |
| 3 | 자가 치유는 **다음 재정렬이 일어나야** 동작한다. 그 사이 사용자는 잘못된 지도를 본다 |
| 4 | 정합성 보장이 앱 로직에만 있어 **DB 단독으로는 검증 불가** |
| 5 | 다중 사용자가 동시에 같은 번지를 조작하면 last-write-wins로 구조가 엉킬 수 있다 |

## 3. 요구사항

| ID | 요구 |
| --- | --- |
| CR3-R1 | 분리 절차 전체(①②③)를 **단일 트랜잭션**으로 처리한다 |
| CR3-R2 | 원복 절차 전체를 **단일 트랜잭션**으로 처리한다 |
| CR3-R3 | 실패 시 **전량 롤백**된다. 부분 반영이 남지 않는다 |
| CR3-R4 | 트랜잭션 종료 시점에 **그룹당 대표 정확히 1개**가 보장된다 |
| CR3-R5 | 대표 승격 규칙(BR-G03)이 SQL에서도 **동일하게 결정적**으로 동작한다 |
| CR3-R6 | 동시 조작 시 같은 유효 키 그룹에 대해 **직렬화**된다 |
| CR3-R7 | 클라이언트 호출 인터페이스는 최소 변경으로 유지한다 |
| CR3-R8 | RPC 실행 권한은 **인증 사용자로 제한**한다(RLS 정책과 일관) |

## 4. 제안 설계

### 4.1 RPC 함수

| 함수 | 입력 | 역할 |
| --- | --- | --- |
| `separate_marker_group` | 분리 대상 마커 id 목록, 새 `group_key`, 선택된 대표 id | 재승격 → 키 부여 → `detached_visible` 리셋을 한 트랜잭션에서 수행 |
| `merge_marker_group_to_lot` | 대상 마커 id 목록(또는 `group_key`) | `group_key` 제거 → 번지 기준 재판정 |

**공통 처리 흐름 (함수 내부)**

```
BEGIN
  1. 대상 그룹 행을 잠금 획득 (SELECT ... FOR UPDATE)   ← CR3-R6
  2. 입력 유효성 검증
     - 선택된 대표가 분리 대상에 포함되는가
     - 대상 마커가 모두 같은 유효 키에 속하는가
  3. 잔여 그룹 재승격 (BR-G03 순서: group_role='대표' 중 created_at 최소)
  4. 분리 대상에 group_key + parent 지정
  5. detached_visible = false 리셋
  6. 사후 검증: 관련 유효 키별 대표 수 = 1
     위반 시 RAISE EXCEPTION → 전량 롤백
COMMIT
```

### 4.2 설계 결정

| 결정 | 이유 |
| --- | --- |
| Supabase RPC(PL/pgSQL) | 클라이언트에서 트랜잭션을 열 수 없으므로 서버 함수가 유일한 원자화 수단 |
| 함수 내부 **사후 검증** 포함 | 규칙 위반을 커밋 전에 차단 (NFR-11 DB 레벨 보장) |
| 행 잠금 사용 | 동시 조작 직렬화 |
| 클라이언트 판정 로직은 **유지** | 미리보기·UI 표시는 계속 앱에서 계산. RPC는 **커밋 경로만** 담당 |
| **[CR-002](./CR-002.md) 선행** | 유효 키 규칙이 하나로 정리된 뒤 SQL로 이식해야 3중 구현이 되지 않는다 |

> ⚠️ 주의: 이 CR은 유효 키 규칙을 **SQL에도 존재하게 만든다.** CR-002로 TS 구현을 1개로 줄인 뒤 진행하지 않으면 TS 2개 + SQL 1개로 상황이 악화된다. **선후 관계를 반드시 지킨다.**

## 5. 변경 범위

| 영역 | 변경 |
| --- | --- |
| 마이그레이션 | 신규 — RPC 함수 2종 정의 (`IF NOT EXISTS` 규칙 준수) |

| 문서 | PRD §5.3 경고 제거, BUSINESS_RULE BR-G05 주석 갱신, ARCHITECTURE §10 G6 해소, DATABASE에 RPC 절 추가 |
| 테스트 | 중단 주입 테스트, 동시 조작 테스트 추가 |

## 6. 영향도

| 항목 | 평가 |
| --- | --- |
| 규모 | **대** — DB 함수 + 데이터 접근 + 모달 |
| 데이터 | 스키마 변경 없음, **함수 추가** 마이그레이션 필요 |
| 회귀 위험 | **높음** — 도메인 최핵심 경로 |
