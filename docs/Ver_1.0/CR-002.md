## 1. 배경

유효 키(Effective Group Key)는 그룹 판정의 **단일 최상위 규칙**이다.

```
effectiveKey(marker) = marker.group_key ?? lotAddressKey(marker.jibun_address)
```

그런데 현재 **동일 규칙이 두 곳에 각각 구현**되어 있다.

| 위치 | 함수 | 입력 형태 |
| --- | --- | --- |
| `lib/address-group.ts` | `getEffectiveGroupKey` | snake_case row |
| `modals/marker-detail-modal.tsx` | `getMarkerEffectiveKey` | camelCase marker |

IA §6.1은 이 상태를 명시적 경고로 남겨두었다: "동일 규칙이 두 곳에 각각 구현되어 있다(검수 항목 G2). 변경 시 반드시 양쪽을 함께 수정한다."

## 2. 문제

| # | 문제 |
| --- | --- |
| 1 | **드리프트 위험** — 한쪽만 수정하면 지도 렌더와 상세 모달의 그룹 판정이 달라진다 |
| 2 | **재현 어려운 버그** — 불일치는 특정 데이터에서만 드러나 원인 추적이 오래 걸린다 |
| 3 | **테스트 공백** — 모달 내부 구현은 순수 함수 테스트 대상 밖이다 |
| 4 | **G1과 결합** — 2,006줄 모달 안에 도메인 규칙이 들어 있어 리뷰 난이도를 높인다 |

### 왜 두 벌이 되었나

DB row는 snake_case, 앱 도메인 타입은 camelCase다. 변환 경계(`api.ts`)를 지나기 전후로 형태가 달라 각각의 접근자를 쓰다 보니 함수가 갈라졌다.

## 3. 요구사항

| ID | 요구 |
| --- | --- |
| CR2-R1 | 유효 키 계산 구현을 **단 하나**로 통합한다 |
| CR2-R2 | snake_case row와 camelCase marker **양쪽 입력을 모두** 지원한다 |
| CR2-R3 | 통합 함수는 `lib/`의 **순수 함수**로 두고 단위 테스트를 붙인다 |
| CR2-R4 | 모달은 통합 함수를 호출만 한다. 자체 구현을 남기지 않는다 |
| CR2-R5 | **동작은 변경하지 않는다.** 순수 리팩터링이며 그룹 판정 결과가 달라져서는 안 된다 |
| CR2-R6 | 기존에 두 구현의 결과가 갈리던 입력이 있다면 **어느 쪽으로 통일했는지 명시**한다 |

## 4. 제안 설계

**정규화 어댑터 방식**

```
lib/address-group.ts

  normalizeGroupFields(input): { groupKey, jibunAddress }
      ├ snake_case row  → group_key, jibun_address
      └ camelCase marker → groupKey, jibunAddress

  getEffectiveGroupKey(input): string
      = normalize → (groupKey ?? lotAddressKey(jibunAddress))
```

| 결정 | 이유 |
| --- | --- |
| 함수 1개 + 입력 정규화 | 호출부 변경 최소화, 두 형태 모두 안전 수용 |
| `lib/`에 배치 | 순수 함수 유지 → 테스트 가능 |
| 모달의 `getMarkerEffectiveKey` **제거** | 중복 원천 제거 |

**대안**: camelCase로만 받도록 강제하고 호출부에서 변환 — 호출부 수정 범위가 커지고 회귀 위험이 높아 반려.

## 7. 검증 계획

**차이 검증 (선행 필수)**

```
1. 운영 백업 데이터를 입력으로 두 구현을 각각 실행
2. 결과가 다른 행이 있는지 전수 비교
3. 차이가 있으면 → 원인 분석 후 어느 쪽이 옳은지 결정하고 CR2-R6에 기록
4. 차이가 없으면 → 통합 후 동일 비교로 무변화 확인
```
