## 1. 배경과 결정 사항

사용자가 시설일정을 매일 쓰는데 "쓸수록 불편한 것"이 쌓이지만 말로 설명하기 어렵다고 했다. 그래서 (1) Claude의 조사 에이전트와 agy가 **서로 모르게** 같은 기능을 점검하고, (2) 두 결과를 대조해 코드로 확인하고, (3) 사용자가 장면 고르기 형태의 질문에 답하는 인터뷰(mattpocock grilling)로 불편을 구체화했다. 이 문서는 그 결과로 **무엇을 어떤 순서로 바꿀지**를 정한다.

### 1.1 사용자가 정한 것 (인터뷰, 2026-11-15)

| # | 결정 |
|---|---|
| 1 | 사용 맥락: 관리자 본인이 PC에서 일정을 입력·수정하고, 다른 사람은 조회·엑셀·메일로 본다 |
| 2 | 불편이 느껴지는 작업: 새 일정 넣기, 고치기·지우기·옮기기, 찾기, 그리고 **"뭔가 모를 반복성 노가다"** |

### 2.2 저장 코드의 구조 (설계의 출발점)

저장 함수는 **판단(순수)** 과 **실행(DB 호출)** 이 이미 나뉘어 있다.

- 판단(순수 함수, 테스트 있음): `planGroupOps`·`planCompanionOps`·`planCrossTeamCreate`·`planWorkDatesCreate`·`planCompanionArrangement`·`planDrop`·`planReschedule`. 결과는 `{ op: "create" | "update" | "delete", … }` 목록이다.
- 실행: 위 목록을 `createScheduleCell`·`updateScheduleCellText`·`deleteScheduleCell`·`moveScheduleCell`(RPC `move_schedule_cell`)로 **한 칸씩** 보낸다. 칸을 옮길 때는 "도착 팀의 가장 작은 빈 행"으로 보내고, 마지막에 행 정리를 위해 다시 조회해서 이동을 반복한다.
- DB: `schedule_cells`는 `(work_date, column_id, row_no)`에 **지연 가능한 UNIQUE 제약**(`schedule_cells_position_key DEFERRABLE INITIALLY IMMEDIATE`)이 있어 한 트랜잭션 안에서 자리를 바꿀 수 있다. 쓰기는 RLS로 관리자만 가능하다. 엑셀 가져오기용 `replace_schedule_cells`는 이미 "한 트랜잭션으로 날짜 범위 교체" 방식이라 같은 패턴을 쓸 수 있다.

## 3. 설계

### 3.1 3단계 로드맵

| 단계 | 내용 | DB 변경 | 상태 |
|---|---|---|---|
| **1A 안전망(화면 쪽)** | 확인창·맞바꿈 알림, 보기 상태 유지, 검색 결과 위치 강조 | 없음 | 이 문서에서 상세 설계 |
| **1B 안전망(저장 쪽)** | 그룹 단위 원자 저장(`apply_schedule_groups` RPC), 저장 실패 시 입력 보존·재시도, 되돌리기(Ctrl+Z·토스트) | **있음**(마이그레이션 1개) | 이 문서에서 상세 설계 |
| **2 반복 줄이기** | 일정 복제, 기간 일정 묶음·일괄 수정, 미배정 연속 배정과 메모, 일일일정 Tab 입력, 검색 필터 | 있음(묶음 정보) | 방향만, 별도 설계 |
| **3 큰 창 재설계** | 한 칸 인라인 편집, 칸 창 단순화(접이식), 주간·월간 이동 규칙 통일 | 없음 | 방향만, 별도 설계 |

### 3.2 1A — 화면 쪽 안전망 (DB 변경 없음)

**A1. 보기 상태 유지** — 새 순수 모듈 `lib/view-state.ts`.
- `localStorage` 키 `schedule-view-v1`: `{ facilityView, weekCount, monthCount, dailyView, visibleOptionalColumnIds[] }`. `sessionStorage` 키 `schedule-date-v1`: `{ selectedDate, weekStart, month, savedOn }` — `savedOn`이 오늘이 아니면 버린다(다음 날 탭을 열어 둬도 어제 주로 열리지 않는다).
- 읽을 때 값을 검증한다(보기 방식은 `week|month`, 주 수 1~4, 달 수 1~3, 선택 열은 **현재 존재하는 열 id만**). 깨졌거나 없으면 기본값. 저장소가 막혀 있어도(`try/catch`) 화면은 정상이다.
- 저장소 접근은 함수 인자로 주입해 `.test.ts`로 검증한다. `ScheduleView`는 첫 렌더에 읽고 값이 바뀔 때 저장한다(`ScheduleView`는 `dynamic()` 패널이라 서버 렌더·하이드레이션 문제가 없다).

**A2. 검색 결과 위치 강조** — 검색 결과(`searchScheduleCells`)는 칸 id·팀·행을 이미 가진다. 결과를 누르면 `jumpToDate`가 날짜로 이동한 뒤 **그 칸을 약 3초 강조**(링 표시)하고 화면 안으로 스크롤한다. 강조 대상은 `ScheduleView`가 `highlightCellId` 상태로 들고 주간 표·월 달력에 내려준다. 칸 요소에는 `data-cell-id`를 단다.

**A3. 확인창과 알림**
- **전체 삭제** 버튼, 그리고 **저장이 한꺼번에 2건 이상을 지우게 되는 경우**에는 저장 직전에 `window.confirm("N건을 삭제합니다. 계속할까요?")`를 띄운다. 한 건 `×` 삭제는 확인 없이 두고 1B의 되돌리기로 보호한다(번거로운 확인을 줄이려는 Q8 ③의 취지).
- 드래그로 **맞바꿈**이 일어나면 토스트로 "A와 B의 자리를 맞바꿨습니다"를 보여 준다(되돌리기 버튼은 1B에서 붙는다). 팀 묶음이 이동하면 "N건을 옮겼습니다"를 보여 준다.

### 3.3 1B — 저장 쪽 안전망 (DB 함수 추가)

#### 핵심 아이디어: "그룹 단위 최종 상태 교체"

칸 단위 요청 여러 개 대신, **영향받는 (날짜, 팀) 그룹마다 그 그룹의 최종 칸 목록**을 만들어 한 번의 DB 호출로 보낸다. 서버는 한 트랜잭션에서 각 그룹의 칸을 최종 목록과 같아지게 만든다. 효과:
- 전부 성공하거나 전부 취소된다(일부만 저장되는 일이 없다). 그래서 **실패해도 창을 닫지 않고 입력을 보존한 채 다시 시도**할 수 있다(지금 창을 닫는 이유가 사라진다).
- 요청 수가 줄어 저장이 빨라진다(수십 번 왕복 → 1번).
- **되돌리기가 쉬워진다**: 저장 직전의 최종 상태(스냅샷)를 같은 함수로 다시 보내면 된다.

#### DB 함수 `public.apply_schedule_groups(p_groups jsonb, p_marks jsonb) returns jsonb`

- `SECURITY INVOKER`, `SET search_path = ''`, 관리자 RLS를 그대로 따른다(`replace_schedule_cells`와 같은 권한 모델, `authenticated`만 실행 허용).
- 입력 `p_groups`: `[{ work_date, column_id, base_ids: [uuid…], cells: [{ id?, row_no, main_text, sub_text, text_color, companion_target?, result_status?, result_reason?, rescheduled_to? }] }]`.
  - **`base_ids`는 클라이언트가 보고 있던 그 그룹의 칸 id 집합**이다. 서버가 실제 그룹의 id 집합과 비교해 다르면 `stale_group` 오류로 전체를 취소한다(다른 곳에서 그 사이 일정이 바뀐 경우). 입력은 보존되고 "다른 곳에서 일정이 바뀌었습니다. 새로 고친 뒤 다시 시도하세요"를 안내한다. **되돌리기에도 같은 보호가 걸린다.**
  - `cells`에서 `id`가 있으면 그 칸을 갱신(국소·모국·장비·글자색·대상 표시·행 번호만; **시행 결과는 건드리지 않는다**), 없으면 새로 만든다(이때만 시행 결과 필드를 함께 넣는다 — 되돌리기로 지워진 칸을 복원할 때 쓴다). 최종 목록에 없는 기존 칸은 삭제한다.
  - 함수 맨 앞에서 `SET CONSTRAINTS public.schedule_cells_position_key DEFERRED`로 자리 충돌을 트랜잭션 끝에서 검사해, 자리 맞바꿈·행 정리가 한 번에 된다.
- 입력 `p_marks`: `[{ work_date, column_id, color|null }]` — 칸 색 표시(`schedule_marks`) 변경.
- 반환: `{ created: [{ group_index, cell_index, id }] }` — 새로 만든 칸의 id(되돌리기에서 "만든 칸 삭제"에 쓰지 않고 스냅샷 복원으로 처리하므로 보조 정보).
- 기존 `move_schedule_cell`·`replace_schedule_cells`는 그대로 둔다(드래그·엑셀 가져오기가 계속 쓴다).

| `lib/undo-stack.ts` | 순수. 최대 20개 스택(`push`·`pop`·`clear`), 항목 = `{ label, before: GroupSnapshot[], marksBefore, after: GroupSnapshot[] }` | 있음 |
| `api.ts`의 `applyScheduleGroups(supabase, groups, marks)` | RPC 호출, `stale_group`·함수 없음 오류를 구분해 던진다 | 오류 변환 테스트 |
| `hooks/use-schedule-write.ts` | `write(label, groups, marks)`: 직전 스냅샷을 스택에 쌓고 RPC 호출, 성공 시 재조회, 토스트 `[되돌리기]`. `undo()`: 스택에서 꺼내 스냅샷으로 복원(복원 때도 `base_ids`로 충돌 검사). 함수가 DB에 없으면(마이그레이션 전) **기존 칸 단위 실행으로 대체**한다(아래) | 훅 자체는 테스트 없음, 순수 부분은 위 모듈에서 |

- **칸 편집 창 저장**: 기존 판단 부분(`groupPlan` 등)은 그대로 쓰고, 실행 부분(`for … await` 약 150줄)을 `applyOpsToGroups` → `write`로 교체한다. 실패하면 `onClose()`를 부르지 않고 창을 연 채 오류를 보여 준다.
- **드래그 이동**: 기존 `moveScheduleCell`(RPC, 원자)을 그대로 쓰되, 이동 전에 출발·도착 두 그룹의 스냅샷을 스택에 쌓는다. 되돌리기는 두 그룹을 스냅샷으로 복원한다.
- **키보드**: 일정표 화면에서 입력칸(`input`·`textarea`·대화상자)이 아닐 때 `Ctrl+Z`가 `undo()`를 호출한다. 토스트의 [되돌리기] 버튼도 같다. 스택이 비면 아무 일도 없다.
- **기존 방식으로 대체(마이그레이션 전)**: `apply_schedule_groups`가 DB에 없으면(PostgREST `PGRST202`/`42883`) 한 번만 안내를 띄우고 기존 칸 단위 실행으로 저장한다(이 경우 입력 보존·되돌리기는 지원되지 않음). 프로젝트 규칙 "적용 전에도 앱이 죽지 않아야 한다"를 지키기 위한 임시 경로이며, 적용이 확인되면 제거한다(구현 문서에 제거 절차를 적는다).

#### 되돌리기의 범위와 한계

- 대상: 칸 편집 창 저장, 드래그 이동·맞바꿈, 날짜·팀 이동, 삭제, 칸 색 표시. 대상 아님: 엑셀 가져오기(`replace_schedule_cells`), 열 이름·팀장 변경, 날짜 메모·작업금지, 일일일정.
- **같은 탭 세션 안에서만 동작한다**(스택은 메모리). 새로고침하면 사라진다. 이유: 스냅샷을 DB에 쌓으면 저장 구조가 커지고, 다른 사람이 그 사이 바꾼 일정을 덮어쓸 위험이 있다.
- **충돌 안전**: 되돌리기 직전에 `base_ids`로 현재 그룹이 저장 직후 상태와 같은지 검사한다. 다른 곳에서 바뀌었으면 되돌리지 않고 안내한다(남의 변경을 덮어쓰지 않는다).

## 4. 범위 밖

- 2·3단계의 실제 구현(별도 설계).
- 되돌리기의 영속 저장(새로고침 후 복원)과 여러 단계 다시 실행(redo).
- 엑셀 가져오기·일일일정·열 설정의 되돌리기.
- 일정 데이터 모델 변경(기간 묶음 컬럼은 2단계).
- 모바일 전용 화면.

## 5. 위험과 검증

- **SQL을 로컬에서 실행할 수 없다**(프로젝트 규칙). 함수는 Claude가 읽어 검토하고, 사용자가 SQL Editor에서 **먼 미래 날짜(예: 2099-01-01)** 로 확인 절차를 실행하게 한다(구현계획 Task 5 — 만든 칸 → 교체 → 충돌 시도 → 삭제). 확인 전에는 클라이언트가 기존 방식으로 대체되므로 앱은 안전하다.
- **최종 상태 시뮬레이션의 정확성**: 기존 실행(칸 단위 + 마지막 행 정리)과 결과가 같아야 한다. **동등성 시험**(메모리 안 가짜 실행기 대 새 계산)이 이를 지킨다. 다르면 화면에 보이는 행 순서가 바뀌므로 가장 중요한 시험이다.
- **엑셀 호환·인쇄**: 데이터 형태(`schedule_cells`)와 내보내기 코드는 바꾸지 않는다. 영향 없음(내보내기·가져오기 테스트가 그대로 통과해야 한다).
- **권한**: `SECURITY INVOKER`라 RLS가 관리자 전용을 계속 강제한다. 비관리자 호출은 실패한다(확인 절차 포함).
- **동시 편집**: `base_ids` 비교가 다른 관리자의 동시 수정을 감지한다(감지하면 전체 취소).
- **저장소 차단**: 보기 상태 저장이 막혀도(사생활 보호 모드 등) 화면은 정상이다.
- **검증**: 단계마다 `npx tsc --noEmit`, `npx eslint . --max-warnings=0`, `npm test`, 임시 distDir 빌드로 홈 First Load JS(282~283 kB)가 늘지 않았는지 확인한다(시설일정은 `dynamic()` 패널이라 영향이 없어야 한다).

## 6. 사용자 확인 필요 항목

1. **되돌리기 범위**: 같은 탭 세션 안(새로고침하면 사라짐), 저장·삭제·이동·색 표시만 되돌린다 — 이 범위로 괜찮은지.
2. **확인창 기준**: 전체 삭제와 2건 이상 삭제 저장에만 묻고, 1건 `×` 삭제는 확인 없이 되돌리기로 보호한다 — 괜찮은지(모든 삭제에 확인을 원하면 알려 달라).
3. **보기 상태 유지**: 보기 방식·주 수·선택 열은 계속 기억하고(localStorage), 보던 날짜·주는 같은 날 같은 탭에서만 기억한다 — 괜찮은지(날짜도 항상 기억하길 원하면 알려 달라).
4. **진행 순서**: 1A를 먼저 구현·확인하고, 그다음 1B(마이그레이션 SQL 적용을 사용자가 한 번 해야 함)로 가는 순서로 괜찮은지.
5. 이 설계를 승인하면 1A의 구현을 agy에게 시작한다.
