# 시설일정 — 국소별 기간 등록 · 국소별 메모 칸 (설계)

작성일 2026-11-08 · 대상: 일정관리 > 시설일정의 칸 편집 창(`schedule-cell-dialog.tsx`)

## 1. 배경 (사용자 피드백)

1. 작업을 등록할 때 팀별로 같이 하는 경우도 있지만, **며칠 동안 같은 일을 하는 경우**가 있다. 기간을 정해 국소를 등록하는 기능이 필요하다.
2. 칸 편집 창의 "모국·장비·메모 (모든 일정 공통)" 칸을 **국소별**로 바꿔 달라. 칸의 가로 폭이 너무 좁으니 지금의 **2배**로 키워 달라.

## 2. 현재 구조 (코드에서 확인한 사실)

- 같은 팀·날짜의 모든 국소가 같은 메모이면 메모 칸을 하나로 합쳐 보여 주고(`mergedMemo`), 저장할 때 모든 줄에 같은 값을 쓴다. 줄마다 메모가 다르면 줄별 입력(`w-40`)으로 보여 준다.
- 공통 메모 칸은 `w-44`(176px), 줄별 메모 입력은 `w-40`(160px)이다. 창 최대 폭은 `SCHEDULE_CELL_DIALOG_MAX_WIDTH_PX`(1024px)이다.
- 같은 날짜의 여러 팀에 복사하는 계획은 `planCrossTeamCreate`(`lib/cross-team.ts`)가 세우고, 국소 칸·입회·신호수 칸을 팀별 빈 행에 만든다. 같은 국소·같은 종류가 있으면 건너뛴다.
- 날짜 계산은 `lib/week.ts`(`addDays`, `weekdayLabel`, `isValidIso`), 공휴일은 `lib/holidays.ts`(`holidayName`)에 있다.

## 3. 목표와 비목표

**목표**
- 국소마다 메모 칸을 보여 주고 저장은 줄별로 한다. 메모 칸 폭을 지금의 2배로 키운다.
- 국소마다 "종료일"을 정해, 그 국소를 시작일(지금 보는 날짜)부터 종료일까지 같은 팀의 날짜별 빈 행에 만든다.
- 기간 안의 토요일·일요일·공휴일은 기본으로 제외하고, 특이한 경우에는 포함할 수 있다.

**비목표**
- DB 구조 변경(마이그레이션 없음). 종료일은 저장하지 않는다. 저장 시점에 날짜별 칸을 만들 뿐이다.
- 작업금지 기간(`schedule_freezes`)을 보고 날짜를 거르는 것. 작업금지는 일정표에 배지로 표시되므로 사용자가 보고 판단한다.
- 이미 만든 기간 일정을 한꺼번에 고치거나 지우는 기능(날짜마다 따로 고친다).
- 기간 등록한 칸의 시행 결과 복사.

## 4. 설계

### 4.1 국소별 메모 칸 (2번)

- `mergedMemo` 상태와 공통 메모 `Textarea`를 없앤다. 국소 행마다 메모 `Input`을 항상 보여 준다(`draft.subText`). `handleSave`의 `entries`는 `drafts` 그대로다.
- 이미 모든 줄이 같은 메모였던 일정도 줄별 입력으로 보이고 값은 그대로다.
- 폭 상수를 `features/shell/constants.ts`에 둔다: `SCHEDULE_CELL_MEMO_WIDTH_PX = 352`(기존 176px의 2배). 메모 입력은 이 폭을 쓰고 컴포넌트에 숫자를 적지 않는다.
- 폭이 늘어난 만큼 창이 좁지 않도록 `SCHEDULE_CELL_DIALOG_MAX_WIDTH_PX`를 1024 → 1200으로 올린다.

### 4.2 국소별 기간 등록 (1번)

**화면**
- 각 국소 행 아래에 한 줄을 더해 `종료일` 날짜 선택(`DatePicker`, 비워 두면 기간 없음)을 둔다. `canEdit`일 때만 보인다.
- 국소 목록 아래 "함께 등록할 팀" 옆에 체크박스 `토·일·공휴일도 포함`(기본 꺼짐)을 둔다.
- 종료일이 시작일보다 이르거나 시작일로부터 31일을 넘으면 저장을 막고 안내한다.

**저장 흐름** (`handleSave`의 기존 저장이 끝난 뒤)
1. 종료일이 있는 국소(이미 있는 국소 포함)만 모은다.
2. 날짜 확장 `expandPeriodDates(startIso, endIso, includeOffDays)`로 시작일 **다음 날부터 종료일까지**의 날짜를 구한다. 기본은 토·일·공휴일을 제외하고, 제외한 날짜와 이유를 돌려준다.
3. 그 날짜 범위의 칸을 `fetchScheduleCells`로 한 번 새로 불러온다(보고 있는 기간 밖일 수 있다).
4. 날짜마다 `planCrossTeamCreate`를 부른다. 대상 팀은 **원래 팀 + 함께 등록할 팀**, 항목은 그 날짜에 포함되는 국소(종료일이 그 날짜 이상인 것), `companions`는 창에서 체크한 입회·신호수다. 이미 있는 국소·입회·신호수는 건너뛴다(기존 규칙).
5. 만든 칸은 `createScheduleCell`로 저장한다. 메모·글자색·"입회·신호수 대상" 표시가 함께 복사된다.
6. 대상 표시가 복사된 팀·날짜는 기존 정리(`planCompanionArrangement`)를 같은 순서로 적용한다(날짜가 여러 개이므로 날짜마다).
7. 저장 후 토스트에 요약한다: `기간 등록: N일 · 칸 M개 생성` 과 건너뛴 날짜(주말·공휴일)·건너뛴 항목(이미 있음·행 부족).

**원자성**: 날짜마다 순차 저장이다. 중간에 실패하면 이미 만든 칸은 남고 오류를 알린 뒤 창을 닫는다(기존 저장 실패 처리와 같다). 같은 항목을 다시 저장해도 "이미 있음"으로 건너뛰므로 중복이 생기지 않는다.

### 4.3 순수 함수 (테스트 대상)

- `expandPeriodDates(input: { startIso: string; endIso: string; includeOffDays: boolean }): { dates: string[]; skipped: { date: string; reason: "weekend" | "holiday" }[] } | { error: "invalid" | "reversed" | "too-long" }` — 시작일 다음 날부터 종료일까지. 최대 31일(시작일 제외 종료일 포함).
- `planPeriodCreate(input: { cells: ScheduleCell[]; startIso: string; targetColumnIds: string[]; entries: (CrossTeamEntry & { endIso: string | null })[]; companions: CrossTeamCompanion[]; includeOffDays: boolean }): { creates: { columnId: string; position: CellPosition; text: ScheduleTextInput }[]; skipped: …; skippedDates: …; dates: string[] } | { error: … }` — 위 4.2의 2~4단계를 순수 계산으로 묶는다(내부에서 `expandPeriodDates`와 `planCrossTeamCreate`를 재사용).

## 5. 오류·경계 조건

- 종료일이 비어 있는 국소는 기간 등록에서 제외된다(오늘 하루만).
- 시작일과 종료일이 같으면 추가 날짜가 없다.
- 기간 안의 모든 날짜가 제외 대상(예: 토·일만)이면 만들 날짜가 없다는 안내를 한다.
- "날짜·팀 옮기기"를 쓰는 저장과 기간 등록을 같이 쓰면 막는다(`crossTeamBlockReason`과 같은 이유).
- 기간 등록은 창이 `canEdit`일 때만 가능하다.

## 6. 테스트

- `expandPeriodDates`: 평일만의 기간 / 토·일 포함 기간에서 기본 제외 / `includeOffDays`로 포함 / 공휴일 제외와 이유 / 종료일이 이른 경우 `reversed` / 31일 초과 `too-long` / 잘못된 날짜 `invalid` / 시작일=종료일.
- `planPeriodCreate`: 날짜마다 같은 행 규칙으로 배정 / 이미 있는 날은 duplicate로 건너뜀 / 팀이 여러 개 / 입회·신호수가 날짜마다 복사 / 항목마다 종료일이 달라 일부 날짜에만 들어감 / 종료일 없는 항목은 제외.
- 메모 칸 폭·공통 칸 제거는 `.tsx`라 단위 테스트가 실행되지 않으므로 코드 검토와 화면 확인으로 본다.

## 7. 구현 순서

1. 국소별 메모 칸과 폭 상수(4.1) — 독립, 바로 효과.
2. 순수 함수 `expandPeriodDates`, `planPeriodCreate`와 테스트(4.3).
3. 창의 종료일·토글 UI와 저장 연결(4.2).

## 8. 가정

- 확인됨: 토·일은 기본 제외하되 특이한 경우 포함할 수 있어야 한다.
- 가정: 공휴일(`holidays.ts`)도 토·일과 같이 기본 제외하고 같은 토글로 포함한다. 작업금지 기간은 거르지 않는다.
- 가정: 기간 등록은 입회·신호수도 날짜마다 같이 복사한다(같은 팀이 며칠 같은 현장에 나가므로).

## 9. 추가 — 일일일정 "작업자(시설팀)" 칸이 비어 있는 문제

**증상**: 일일일정의 작업자 칸이 비어 있다. 시설일정에서 국소가 들어간 팀의 팀장 이름이 기록되어야 한다(국소가 1팀·4팀에 있으면 두 팀장 이름을 쉼표로 이어서).

**조사 결과 (코드 결함 아님)**
- 작업자 칸은 이미 `buildDayStations`가 국소를 맡은 팀 열의 `leaderLabel`을 모아 쉼표로 잇는다(`lib/day-stations.ts`, `lib/day-rows.ts`의 `values.worker`). 같은 국소가 여러 팀에 있으면 팀 순서대로 이어 붙고 `day-rows.test.ts`가 이를 확인한다.
- 비어 보이는 이유는 DB의 `schedule_columns.leader_label`이 모든 팀에서 빈 값이기 때문이다. 팀장 이름은 직원 실명이라 마이그레이션·저장소에 넣지 않고 앱 화면이나 엑셀 가져오기로 입력하기로 했었다(`20261108000000_facility_schedule.sql` 머리말).
- 저장된 일일일정 상세(`schedule_day_details`)가 없고, 작업자를 비워서 저장한 기록도 없어 팀장 이름을 입력하면 바로 반영된다.

**조치**: 코드 변경 없음. 사용자가 시설일정 화면에서 팀 머리글(1~7팀)을 눌러 "팀 머리글 수정"의 **팀장** 칸에 이름을 입력한다(또는 엑셀 가져오기의 두 번째 머리 행). 입력 뒤 일일일정에서 같은 국소가 들어간 팀의 팀장이 쉼표로 이어져 나오는지 확인한다. 이름은 이 문서와 저장소에 적지 않는다.

**유의**: 일일일정에서 한 국소의 작업자 칸을 직접 고쳐 저장하면(`detail.worker`) 이후에는 팀장 이름이 바뀌어도 자동값이 아닌 저장한 값이 쓰인다. 빈 문자열로 저장한 경우도 마찬가지다.
