# Ver 3.0 위치등록 신규 확인 구현

근거: `Ver_3.0_계획.md` 3장(재업로드 초기화), 5장(옛 양식), 11장.

## 행 분류

| 구분 | 조건 | 처리 |
|---|---|---|
| `new` | DB에 없는 통합시설코드 | 확인 목록 → [확인] 시 마커·공정 정보 저장 |
| `missingCoords` | DB에 있고 좌표 없음 | 확인 목록 → [확인] 시 국소명·좌표·공정 정보 저장 |
| `existing` | DB에 있고 좌표 있음 | [기존 N건 갱신] 시 국소명·공정 정보 저장 |
| 코드 없음 | 통합시설코드 빔 | 저장하지 않고 안내 |
| 주소 없음 | 주소가 비었거나 `불필요`·`미확정` | 저장하지 않고 안내. 이미 등록된 코드여도 갱신하지 않음 |

## 사업연도 (A열)

공정_일정관리.xlsb의 A열에는 사업연도가 있고 헤더 칸이 비어 있다. **첫 열의 헤더가 비어 있으면 `사업연도`로 읽는다**(`erp-parse.ts`). 시설연도는 이 값을 가장 먼저 쓰고, 비면 시설연도 열 → 프로젝트 코드 → 국소명 `26Y_` → ACTA 구축완료일 순으로 구한다.

**같은 통합시설코드라도 사업연도가 올해 이상(올해·미래)이면 시설을 진행하는 별개 건이다.** 기존 마커의 시설연도(`information.facility_year`)와 비교해 분류한다(`erp-classify.ts`).

| 행의 사업연도 | DB에 같은 코드의 마커 | 처리 |
|---|---|---|
| 올해 이상 | 같은 연도(또는 연도를 모르는) 마커 있음 | 그 마커에 연결 — 기존 건. 같은 파일을 다시 올려도 중복이 생기지 않는다 |
| 올해 이상 | 다른 연도 마커만 있음 | **새 마커.** ID는 `erp_코드_연도`(예: `erp_202621972_2027`) |
| 올해 이상 | 없음 | 새 마커 `erp_코드` |
| 지난 연도·빈 값 | 진행 중(올해 이상)이 아닌 마커 있음 | 예전처럼 코드로 연결 |
| 지난 연도 | 진행 중인 마커만 있음 | 저장하지 않음(`지난 사업연도`). 진행 중인 건의 공정 정보를 덮지 않기 위해서다 |
| 빈 값 | 진행 중인 마커만 있음 | 예전처럼 코드로 연결(연도를 몰라 판단하지 않는다) |

"올해"는 업로드하는 날의 연도다. 연도가 바뀌면 지난해 마커는 지난 연도로 취급된다.

같은 코드가 파일에 여러 번 나오면 DB의 같은 코드 마커에 순서대로 연결하고, 남는 행은 `erp_코드_n` ID의 신규로 본다. 통합시설코드가 `끝`인 행은 양식의 데이터 끝 표시이므로 그 행에서 읽기를 멈춘다(`erp-columns.ts`).

분류는 `erp-classify.ts`, 저장은 `erp-review-save.ts`, 주소 대조는 `address-compare.ts`에 있고 모두 업로드·확인할 때 지연 로딩한다. 임시 저장(`erp-review.ts`)만 항상 로드한다.

## 저장 규칙

- 신규는 전체 열을 저장하되 같은 ID가 이미 있으면 덮어쓰지 않는다.
- 기존 건 마커에는 `id`·`name`·`facility_code`(좌표 없는 건은 `lat`·`lng`까지)만 보낸다. 나머지 열은 유지된다.
- 공정 정보(`information`·`erp_details`)는 삭제 후 다시 넣고, 삭제 오류도 확인한다. 저장 원자성은 이번 범위가 아니다.
- 기존 마커 조회는 `fetchAllRows`로 1000건 제한을 피한다.
- 대표/SUB 재정리는 건별로 하지 않는다. 목록을 끝낼 때, [나중에 이어서], 취소, 기존 건 갱신, 임시 저장 복원 때 필요한 경우에만 실행한다.

## 대표/SUB 재정리와 단독

같은 번지 주소(또는 `group_key`)의 마커는 가장 먼저 등록된 것이 대표, 나머지가 SUB다(`address-group.ts`의 `applyMarkerRolesFromStoredGroupRole`). 저장된 `단독`은 주소에 따라 다르게 본다.

- **그 주소에 대표·SUB가 이미 있으면** `단독`은 그룹관리·상세 화면에서 직접 분리한 것으로 보고 그대로 둔다.
- **그 주소가 단독뿐이면** 혼자일 때 자동으로 붙은 값이므로, 같은 주소 마커가 새로 등록될 때 함께 대표 + SUB로 묶는다.
- 한계: 두 마커짜리 그룹에서 한쪽을 분리하면 둘 다 단독이 되어, 나중에 같은 주소 마커가 들어오면 함께 묶인다(의도한 분리와 자동 단독을 값만으로는 구분할 수 없다).
- 이 규칙은 재정리가 실행될 때만 적용된다(위치등록 마무리, [나중에 이어서], 사이드바 "구분 재정리"). 2026-11-10 기준 DB에서는 5개 주소 26건이 단독을 유지하고 1개 주소 2건(`화순군 춘양면 우봉리 산30-1번지`)이 묶인다.

## 마커주소

`road_address`(도로명)·`jibun_address`(지번)는 엑셀에서 올린 주소이고, **`markers.marker_address`(마커주소)는 마커가 놓인 좌표의 주소**(도로명 우선)다. 엑셀 주소와 같든 다르든 저장한다.

- 저장 시점: 확인 목록의 [확인](주소가 달라 `그래도 저장`한 경우 포함)과, 저장된 장비 마커를 지도에서 끌어 옮길 때. 옮긴 뒤 주소를 못 구하면 옛 값이 남지 않게 비운다.
- 위치 저장과 따로 쓴다(`marker-address.ts`). 컬럼이 없는 DB(`20261117000000_marker_address.sql` 적용 전)에서도 위치 저장은 성공하고, 확인 저장은 마커주소를 못 남겼다는 안내를 띄운다.
- 표시: 상세 모달 `지번` / `도로명` / `마커주소`, 지도 말풍선 `지번` → `(도로명)` → `(마커주소)`. 이미 등록된 마커는 위치를 다시 저장하거나 옮기기 전까지 비어 있다.
- 저장된 값이 없는 마커(예전 등록분)는 상세 화면에서 좌표를 주소로 바꿔 확인한다(`use-marker-address-display.ts`). 등록 주소와 같은 곳이면 등록 주소(지번 우선), 다르면 좌표의 실제 주소를 보여 주고, 화면에만 표시할 뿐 DB에는 쓰지 않는다.
- 도로명 주소: 엑셀 주소는 지번뿐이라 `road_address`가 비어 있다. 상세 모달은 저장된 값이 없으면 좌표를 주소로 바꿔, **등록 지번과 같은 곳일 때만** 그 도로명 주소를 보여 준다(다른 곳으로 옮긴 마커의 도로명은 이 국소의 것이 아니다). 도로명 주소가 없으면 `도로명 주소 없음`으로 표시하고, 화면에만 표시할 뿐 DB에는 쓰지 않는다.
- 주소 칸: 공정관리 가져오기(백업 복원, `parseErpStyleBackupToTables`)가 예전에는 엑셀 주소를 전부 `road_address`(신주소)에 넣어 지번이 신주소로 보였다. 이제 주소 종류를 판별해 `jibun_address`/`road_address`로 나눠 넣는다. 이미 저장된 데이터는 `20261117000100_split_jibun_from_road_address.sql`로 바로잡는다(2026-11-10 기준 1,068건 대상, 사용자가 적용).
- 전체 백업·복원의 `markers` 열 목록에 포함한다(마이그레이션 적용 전 DB에 복원하면 이 열 때문에 실패하므로 먼저 적용한다).

## 주소 대조

`isSameAddress(엑셀 주소, 좌표의 도로명·지번 주소)`

- 엑셀 주소가 지번이면 동·리·가 이름과 번지(산 포함)를, 도로명이면 도로명과 건물번호를 비교한다.
- 시도 표기(`광주광역시`/`광주`)는 비교하지 않는다. 시·군·구는 엑셀 주소에 있을 때만 비교한다.
- 비교할 수 없으면(좌표의 주소 없음, 엑셀 주소를 해석할 수 없음) 다른 주소로 취급해 사용자에게 보여 준다.

## 임시 저장

- 키: `map-marker-erp-draft:<사용자 ID>` (`localStorage`). 확인 목록과 재정리 필요 여부만 저장하고, 기존 건은 저장하지 않는다. 기존 건은 파일을 다시 올려 갱신한다.
- 스토어 구독은 항상 마운트된 `map-marker-page`에서 한다. 패널을 닫은 채 마커를 옮겨도 저장된다.
- 파일을 다시 올리면 같은 ID의 옮긴 위치를 유지한다.

## 화면

- 확인 목록(`erp-review-panel.tsx`): [확인], 위치 보기, 제외, 주소 못 찾은 건의 [지도에서 찍기].
- 드래그는 위치만 바꾼다. 저장은 [확인]으로만 한다.
- 확인 목록 마커의 수정 화면은 막는다. 공정 정보 없이 저장되어 확인 절차를 건너뛰기 때문이다.

## 추가 사업 (같은 코드·같은 연도, 다른 프로젝트코드)

통합시설코드와 사업연도가 같아도 프로젝트코드가 다르면 다른 사업이다(예: 신설 뒤의 부대장비증설). 같은 마커에서 따로 관리해야 하므로 덮어쓰지 않고 상세 행으로 덧붙인다.

- 올해 이상 행만 대상이다. 마커의 프로젝트코드(`information.project_code`)를 알고, 행의 프로젝트코드가 비어 있지 않으며, 둘이 다르면 `addon`으로 분류한다. 좌표 변환·위치 확인은 없다.
- `addon`은 확인 목록이 아니라 `addonRows`로 가고, 패널의 **추가 사업 N건 반영** 버튼이 `information`·`erp_details`에 **삽입만** 한다. 마커와 기존 행은 건드리지 않는다. 임시 저장에는 넣지 않는다(기존 건과 같다. 파일을 다시 올린다).
- 같은 파일에 기존 사업 행과 추가 사업 행이 함께 있어도 새 마커는 만들지 않는다.
- **기존 건 갱신**도 같은 원칙이다. 프로젝트코드가 있는 행은 같은 프로젝트(와 프로젝트가 빈 옛 행)만 지우고 다시 넣는다(`deleteProjectRowsGuarded`). 신설 행이 파일에서 빠져 있어도 갱신이 신설 정보를 지우지 않는다. 프로젝트코드가 빈 행은 예전처럼 마커의 행을 모두 교체한다.

## 반영 전 변경 내용 확인

[기존 N건 갱신]과 [추가 사업 N건 반영]은 건수만 보여서 무엇이 바뀌는지 알 수 없었다. 두 버튼은 이제 바로 저장하지 않고 **변경 내용 창**(`erp-changes-dialog.tsx`)을 먼저 연다. 창의 [적용]을 눌러야 기존 저장 로직(`refreshStagedExisting`·`addStagedAddons`)이 실행되고, [닫기 (적용 안 함)]은 아무것도 바꾸지 않는다.

- **기존 건 갱신**: DB의 현재 국소명·상세 값과 파일 값을 비교해 바뀌는 칸만 `이전 → 이후`로 보여 준다(`previewExistingRow`). 비교 칸은 국소명, 프로젝트코드, 사업연도, 사업구분, 국소명-최종, 장비 대분류, 장비타입, 시설일, 개통일이다. 빈 값·null·공백은 같은 것으로 본다. 같은 프로젝트코드의 DB 행과 비교하고(갱신이 지우는 범위와 같다), 같은 프로젝트의 DB 행이 없으면 "상세 행: 새로 추가"로 보인다. 기본은 **변경 있는 건만** 보며 체크를 풀면 변경 없음까지 본다.
- **추가 사업**: 새 행으로 들어갈 값(빈 값 제외)을 보여 준다(`previewAddonRow`). 시설일이 비면 마커 상태가 '미시설', 개통일이 비면 '시설'로 바뀔 수 있어(`facility-status.ts`) 주의 칸에 경고를 붙인다. 공정 파일의 시설일이 `불필요`이면 날짜가 아니라 빈 값으로 저장되므로 이 경고가 뜬다.
- 미리보기는 업로드할 때 DB에서 국소명과 상세 9개 칸을 함께 읽어 만든다(`StagedErpRow.preview`). 저장되지 않고 임시 저장에도 넣지 않는다.
- 한계: [적용]은 창에 보이는 건 전체를 저장한다(변경 없음 포함). 행별로 골라 적용하는 기능은 없다.

## 확인 목록의 대표/SUB 그룹

같은 지번에 단지가 여러 곳이면 번지 기준 자동 그룹(먼저 등록된 것이 대표)으로는 원하는 묶음을 만들 수 없다. 확인 목록에서 직접 묶는다.

- 행마다 체크박스. 체크한 행에 **대표** 선택(라디오)이 나온다. [그룹으로 묶기]는 2건 이상 체크하고 대표를 골랐을 때만 켜진다. 나머지 체크 행은 SUB다.
- 묶으면 그룹마다 `group_key`(`번지#묶음#대표 마커ID 전체`)를 만들고, 행의 `group`과 저장할 마커 행에 `group_key`·`group_role`을 싣는다. [확인] 때 마커와 함께 저장되고, 저장 뒤 재정리가 이 키를 우선해 `parent_marker_id`를 맞춘다. DB 변경은 없다.
- 이미 묶인 행을 다시 묶거나 [그룹 해제]를 누르면 그 행이 속한 그룹을 통째로 푼다(대표 없는 그룹이 남지 않게).
- 묶지 않은 행은 예전처럼 번지 기준 자동 그룹이다. 그룹 값은 확인 목록과 함께 임시 저장돼 [나중에 이어서]에도 유지된다.
- 키에 ID 전체를 넣는 이유: `buildSplitGroupKey`는 시드 앞 8자만 써서 `erp_2026…` ID끼리 키가 겹쳤고(2026-11-11 발견), 같은 지번의 서로 다른 묶음이 한 묶음처럼 이동·저장됐다.
- 한계: DB에 이미 있는 마커의 그룹에 새 행을 합류시키는 것, 기존 건·추가 사업 행의 그룹 지정은 하지 않는다. 묶음 대표만 제외하면 남은 SUB는 재정리 때 먼저 등록된 것이 대표가 된다.
- 코드: `lib/erp-review-group.ts`(묶기·해제·번호), `components/sidebar/erp-review-panel.tsx`(체크·대표·배지).

### 묶은 그룹은 한 덩어리로 이동·저장

묶은 행은 개별 마커처럼 따로 옮기고 저장하면 그룹의 의미가 없다.

- **이동**: 지도에서 묶인 대기 마커 하나를 끌면 같은 그룹(대표·SUB)의 대기 마커가 **같은 이동량**으로 함께 움직인다(상대 위치 유지). 스토어 `moveStagedGroup` → `erp-review.ts`의 `moveGroupedPendingMarkers`. 묶이지 않은 마커는 예전처럼 자기만 움직인다. 토스트에 그룹 건수가 나온다.
- **저장**: 묶인 행의 [확인]은 그룹 전체를 한 번에 저장한다(`confirmStagedMarker`).
  - 주소 대조는 **누른 행 기준 한 번**만 한다. 다르면 그룹 전체를 저장하지 않고, [이 위치로 저장]을 누르면 전체를 저장한다.
  - 각 행은 자기 대기 위치로 저장하고, 마커주소는 누른 행에서 구한 값을 그룹 전체에 쓴다(함께 옮긴 같은 자리라는 전제).
  - 그룹에 위치가 없는 행이 있으면(주소를 못 찾음) 저장하지 않고 알린다. 지도에서 찍은 뒤 다시 확인한다.
  - 도중에 실패하면 이미 저장된 행만 목록에서 빼고 나머지는 남긴다. 토스트에 몇 건이 저장됐는지 나온다.
- **목록에서 묶음 위치 지정**: 같은 지번 행은 지오코딩 좌표가 같아 마커가 한 점에 겹치므로, 지도에서 끌면 맨 위 마커(다른 묶음)가 잡힌다. 그래서 행의 📍 버튼(큰 창은 `지정`)을 누르고 지도를 클릭하면 **그 행이 속한 묶음 전체**가 그 자리로 옮겨진다(`moveStagedGroup`). 위치가 없던 행은 예전처럼 그 자리에 놓인다. 위치를 정한 뒤 [확인]을 누르면 그 묶음만 일괄 저장한다.
- **선택한 마커를 맨 위로**: 같은 자리에 겹친 마커 중 목록에서 고른(선택한) 마커는 지도에서 항상 맨 위(`zIndex` 100)에 그린다(`kakao-map-canvas.tsx`). 그래서 목록에서 103동을 고르면 지도에서 보이고 끌리는 핀이 103동 것이다. 선택하지 않은 겹친 마커는 아래에 깔린다.
- 한계: 아무것도 선택하지 않고 겹친 핀을 끌면 맨 위 마커의 묶음이 움직인다. 먼저 목록에서 대상을 고른 뒤 끌거나 📍 버튼을 쓴다.

### 크게 보기 창

사이드바(380px)에서는 국소명과 주소가 잘려 한눈에 보기 어렵다. 그룹 도구줄의 **크게 보기**를 누르면 넓은 창(`ERP_REVIEW_DIALOG_MAX_WIDTH_PX` = 1400)이 열린다.

- 표 한 줄에 체크 · 묶음 · 대표 · 국소명 · 주소 · 작업(위치/확인/제외)이 다 보인다. 셀은 줄바꿈하지 않고 가로 스크롤도 없다(세로 스크롤만). 긴 이름은 말줄임이고 마우스를 올리면 전체가 보인다.
- 체크·대표 선택·그룹 묶기/해제는 사이드바 패널과 **같은 상태**다(`hooks/use-erp-review-groups.ts`). 창에서 묶으면 패널에도 바로 보인다.
- [확인]과 주소 불일치 경고(이 위치로 저장)도 창 안에서 처리한다. 지도가 필요한 [위치]와 [지도에서 찍기]는 창을 닫고 지도로 이동한다.
- 코드: `components/sidebar/erp-review-dialog.tsx`.
