작성일 2026-11-15 · 대상: 홈(`/`) First Load JS 301 kB · 구현계획: [Ver_3.0_홈번들점검_구현계획.md](Ver_3.0_홈번들점검_구현계획.md) · 구현: [Ver_3.0_홈번들점검_구현.md](Ver_3.0_홈번들점검_구현.md)

## 1. 배경과 결정 사항

AGENTS.md의 기준은 홈 First Load JS **295 kB 이하**인데, 현재 **301 kB**다. 번들문서정리(2026-11-14)는 `xlsx`·Leaflet 지연 로드와 선로딩 조건을 바꿨지만 홈 수치는 299 → 300 → 301 kB로 줄지 않았다. 기준선을 넘은 시점과 원인은 확인하지 않았다(작업 폴더에 커밋되지 않은 변경이 섞여 있었다). 이 문서는 **어디에 무게가 있는지 측정하고, 줄일 후보와 결정 기준을 정한다**.

**설계에서 정한 것(사용자 확인 대상은 §6)**

| # | 결정 |

| 3 | 목표는 둘 중 하나다: 295 kB로 되돌리거나, 295 kB 기준을 근거를 붙여 새 값으로 바꾼다(§6) |

## 2. 확인한 사실

### 2.1 현재 수치 (2026-11-15, 임시 distDir 빌드)

### 2.2 홈 페이지 청크 구성 (gzip, 합 294.1 kB)

각 청크가 무엇인지는 청크 안의 문자열로 추정했다(정확한 모듈 단위 측정은 Task 1).

| 청크 | gzip | 추정 내용 |
|---|---:|---|
| `app/page-…` | 65.0 kB | 앱 코드 — 지도 캔버스·정보창·클러스터·오버레이 등(`kakao`·`overlay-`·`cluster` 문자열 다수) |
| `4300-…` | 58.2 kB | Supabase 클라이언트(`supabase` 45회, `GoTrue`) |
| `4bd1b696-…` | 53.1 kB | React DOM |
| `1255-…` | 45.3 kB | Next 런타임 |
| `3732-…` | 32.8 kB | Radix(드롭다운·다이얼로그) + zustand + ts-pattern |
| `44530001-…` | 13.0 kB | Supabase 클라이언트의 나머지 부분(`supabase`·`GoTrue`) |
| `5307`·`3935`·`4314` | 8.8·7.4·7.0 kB | Radix 일부, TanStack Query, 카카오 SDK 로더 등 |
| `webpack`·`main-app` | 3.5 kB | 런타임 |

- **Supabase 클라이언트가 약 71 kB**로 가장 크다. 이 앱은 인증·`from()`·`rpc()`만 쓰고 `storage`·`realtime`·`functions`는 쓰지 않는 것으로 보이나(구현 전 `grep`으로 재확인), `@supabase/supabase-js`는 그 모듈들을 함께 묶는다. 로그인 판정이 첫 화면에 필요해서 지연 로드는 어렵다.
- **페이지 청크(65 kB)** 안에 영역 캡처 UI가 정적으로 들어 있다. `kakao-map-canvas.tsx`가 `MapRegionSelectOverlay`·`MapRegionBoundsGuide`·`MapRegionCapturePanel`(합 약 1,500줄)과 `map-viewport-capture`(613줄)·`map-capture-stitch`를 정적 import한다. 캡처는 사용자가 버튼을 눌러야 쓰는 기능이다.
- React DOM(53 kB)과 Next 런타임(45 kB)은 줄일 수 없다.

### 2.3 이미 지연 로드된 것

대시보드, 일정, 그룹관리, CCTV, 바코드, 지적도(Leaflet), `xlsx`·`exceljs`, 업로드용 데이터 관리자(`excel/data-manager`)는 이미 `dynamic()` 또는 `import()`다. 남은 후보는 위 표의 페이지 청크와 Supabase다.

## 3. 설계

### 3.1 후보 목록과 평가 기준

| 후보 | 내용 | 기대 | 위험 | 비고 |
|---|---|---|---|---|
| **L1** Supabase 클라이언트 줄이기 | `supabase-js` 대신 `auth-js`+`postgrest-js`를 직접 조립해 `storage`·`realtime`·`functions` 제거 | 최대(수 kB~수십 kB, 측정 필요) | 높음 — `SupabaseBrowserClient` 타입을 쓰는 곳이 많고 호환 계층이 필요하다. 라이브러리 내부 구조에 기댄다 | 측정에서 해당 모듈이 실제로 큰 비중일 때만 |
| **L2** 영역 캡처 UI 지연 로드 | 캡처 관련 컴포넌트 3개와 캡처 라이브러리를 `dynamic()`/`import()`로 분리, 열 때 받는다 | 중(약 1,500줄 + 613줄분, 측정 필요) | 낮음 — 사용자가 버튼을 눌러야 나타나는 UI | [대형파일분할2차](../대형파일분할2차/Ver_3.0_대형파일분할2차_설계.md)의 캡처 가이드 훅 분리와 한 묶음으로 하면 경계가 깔끔하다 |
| **L3** 그 밖의 정적 import | 페이지 청크 모듈 측정에서 크게 나온 것(`overlay-drag`, `parcel-boundary`, 클러스터 아이콘, 정보창 HTML 등) 중 평상시 화면에 필요 없는 것 | 측정 필요 | 중 | Task 1 결과로 후보를 뽑는다 |
| **L4** 기준선 조정 | 295 kB를 새 값으로 바꾼다 | — | 기준이 느슨해진다 | 줄일 수 있는 만큼 줄인 뒤 남은 값을 근거와 함께 기록한다 |

평가 기준: ① 측정한 절감량(gzip kB), ② 변경 범위(파일 수), ③ 첫 화면 체감(필요한 순간에 지연이 생기는가). 캡처처럼 "누른 뒤 한 번 받는" 기능은 지연이 허용되고, 로그인·지도 초기화처럼 첫 화면에 필요한 것은 허용되지 않는다.

### 3.2 측정 방법

1. `next.config.ts`에 임시로 `distDir: '.next-build-check'`와 `productionBrowserSourceMaps: true`를 넣고 빌드한다(개발 서버가 떠 있으므로 임시 distDir을 쓰고 끝나면 설정을 원복한다).
2. 홈 페이지의 청크 11개(`app-build-manifest.json`의 `/page`)를 소스맵으로 분해해 모듈(패키지·소스 파일)별 크기를 표로 만든다. 도구는 `npx source-map-explorer`를 우선하고, 받을 수 없으면 소스맵 `sourcesContent`와 `mappings`로 직접 집계하는 스크립트를 스크래치 폴더에 둔다. 프로젝트에 의존성을 추가하지 않는다.
3. 결과를 패키지별(`@supabase/*`, `react-dom`, `next`, `@radix-ui/*` 등)과 프로젝트 소스 상위 30개 파일로 나눠 기록한다.

## 4. 범위 밖

- Cloudflare Workers 쪽 번들(서버 번들 크기)과 `/gpsmap` 최적화.
- 카카오 SDK·VWorld 등 외부 스크립트 자체의 크기.
- React 19·Next 15 업그레이드.

## 5. 위험과 검증

- **측정 오차**: 빌드마다 청크 이름이 바뀌고(해시) 일부 수치가 ±1 kB 움직인다. 비교는 같은 방법(임시 distDir, gzip 합)으로 한다.
- **지연 로드의 부작용**: 처음 누를 때 청크를 받는 동안 지연이 생긴다. 로딩 표시를 두고, 사용 직전에 미리 받는 방법(버튼에 마우스를 올릴 때 `import()`)을 쓸 수 있다.
- **검증**: 변경마다 `npx tsc --noEmit`, `npx eslint . --max-warnings=0`, `npm test`, 임시 distDir 빌드의 홈 First Load JS를 기록한다.

## 6. 사용자 확인 필요 항목

1. **목표**: 295 kB로 되돌린다(추천) / 근거를 붙여 기준을 새 값으로 바꾼다. 현재 6 kB가 넘는 상태라 L2만으로 닿을 수도 있어, 측정 뒤에 정해도 된다.
2. **L1(Supabase 클라이언트 교체)**: 측정에서 큰 절감이 확인될 때만 검토하자는 안을 추천한다. 라이브러리를 직접 조립하는 일은 이번 점검에서 시작하지 않는다.
