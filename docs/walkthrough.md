## [2026-06-09] 로컬 개발 서버 프록시 요청 타임아웃 및 예외 처리 보강 구현 결과

### 1. 개요 및 목적
- 웹 애플리케이션 사용 도중 화면이 갑자기 멈추거나 백색 화면으로 바뀌어 멈추는 현상의 주요 원인 중 하나인 `server.js` 프록시(`/api/roadview-dates`)의 무한 Hanging 현상을 해결하고, 서버 측 비정상 종료(크래시) 요소를 제거하여 시스템 신뢰도를 보강했습니다.

### 2. 변경된 내용
- **`server.js` API 프록시 예외 차단 (`try-catch`)**:
  - `req.url.startsWith('/api/roadview-dates')` 처리부를 `try-catch`로 포장하여, URL 파싱이나 카카오 호출 시 발생하는 런타임 오류가 발생하더라도 Node.js 로컬 서버 프로세스가 멈추거나 죽지 않도록 방어했습니다.
- **`https.get` API 프록시 요청 타임아웃 구현**:
  - `https.get` 리스너를 호출한 `ClientRequest`에 `.setTimeout(5000)` 처리를 추가하여 5초 이상 응답이 오지 않는 경우 강제로 소켓 연결을 제거(`destroy()`)하고 `timeout` 에러 이벤트를 트리거하도록 보완했습니다.
  - 에러 처리 이벤트 `.on('error')` 핸들러에서 에러 종류가 `timeout`인 경우에는 브라우저에 `504 Gateway Timeout` 상태 코드와 명확한 사유를 포함한 JSON 응답(`{"error":"카카오 API 요청 시간이 초과되었습니다."}`)을 리턴하도록 처리했습니다.
  - 기타 일반 에러의 경우 `500 Internal Server Error` 및 에러 JSON 메시지를 반환합니다.
  - CORS 차단을 막기 위해 모든 오류 응답 헤더에 `Access-Control-Allow-Origin: *`를 삽입했습니다.

### 3. 검증 결과
- **정상 응답 검증**: `server.js` 구동 후 `curl.exe`를 통해 `/api/roadview-dates?panoId=1142512683`를 호출했을 때, 카카오 로드뷰 데이터가 CORS 헤더와 함께 `200 OK`로 성공적으로 중계 전달됨을 확인했습니다.
- **타임아웃 시뮬레이션 및 복원성 검증**:
  - `server.js` 타임아웃을 강제로 `1`ms로 수정한 뒤 카카오 API를 중계 요청했습니다.
  - **결과**: `HTTP/1.1 504 Gateway Timeout` 응답이 즉각 반환되었으며, 서버 터미널에는 `프록시 API 요청 오류: Error: timeout` 스택트레이스만 기록되고 서버 자체는 다운되지 않고 계속 가동 중 상태가 유지되는 것을 검증했습니다.
- **안정성 검증 후 원복**: 검증이 무사히 완료된 것을 확인한 후 타임아웃 설정을 정상 프로덕션 스펙인 `5000`ms(5초)로 복원 완료했습니다.

- **CRUD 실시간 동기화**: 마커 편집을 통해 색상을 다른 색으로 변경하여 저장했을 때, 필터 드롭다운 내 목록과 지도 마커 핀이 실시간 갱신되어 필터링 범위가 유기적으로 작동함을 검증 완료했습니다.

## [2026-06-09] 구주소 "번지" 접미사 동적 표시 기능 구현 결과

### 1. 개요 및 목적
- 사용자가 지도상의 마커 정보창(말풍선 오버레이), 상세/등록/수정 모달, 장소 및 주소 검색 결과 등에서 구주소(지번 주소)를 확인하고 드래그/복사할 때 가독성을 향상시키기 위해, 지번 주소가 숫자로 끝나는 경우에만 "번지"를 동적으로 추가하여 출력하도록 개선하였습니다.
- DB에 저장된 원본 주소 데이터는 손상 없이 온전히 보존하여 외부 API 연동 정합성을 유지합니다.

### 2. 변경된 내용
- **`app.js` 내 지번 주소 포맷터 함수 구현 (`formatJibunAddress`)**:
  - 문자열을 받아 끝이 숫자로 끝날 때만(예: "선암동 657" ➡️ "선암동 657번지") "번지"를 안전하게 붙여 반환하고, 이미 번지가 붙어 있거나 숫자로 끝나지 않는 경우는 원본을 그대로 반환하는 범용 포맷터를 정의했습니다.
- **UI 노출 영역 렌더링에 포맷터 연동**:
  - **모달**: 등록 모달(`openAddMarkerModal`), 상세 모달(`openDetailMarkerModal`), 수정 모달(`openEditMarkerModal`) 내에서 (지번) 주소를 표시할 때 `formatJibunAddress`를 적용했습니다.
  - **말풍선 오버레이**: 마커 클릭 시 발생하는 지도 오버레이(`createOverlayContent`) 내 주소 출력 영역 및 핀 이동 시 실시간 오버레이 갱신(`updateOverlayAddress`) 로직에 적용했습니다.
  - **검색 결과 리스트**: 장소/주소 검색 결과 리스트(`displaySearchResults`) 및 결과 클릭 시 생성되는 임시 핀 말풍선 오버레이에 노출되는 지번 주소에 적용했습니다.

### 3. 검증 결과
- **동적 번지 생성 검증**: 
  - 지번 주소가 "선암동 657"인 마커 상세조회 시 화면에 `(지번) 선암동 657번지`로 올바르게 포맷팅되어 나타나는 것을 확인했습니다.
  - 지도 말풍선 정보창과 주소 검색 결과 리스트, 임시 마커 오버레이 등 모든 UI 영역에서 `657번지`, `735-17번지`와 같이 "번지"가 정상 표시됨을 확인했습니다.
- **예외 및 오동작 방지 검증**:
  - 이미 "번지"가 붙은 주소(예: "역삼동 123번지")를 등록/조회할 경우 `역삼동 123번지번지`처럼 중복 처리되지 않고 `역삼동 123번지`로 정상 렌더링됨을 확인했습니다.
  - 숫자가 아닌 단어로 끝나는 주소(예: "선암동")의 경우 "번지"가 붙지 않고 정상 출력됨을 확인했습니다.

## [2026-06-08] DB 주소 저장 방식을 통한 카카오 Geocoder API 호출량 최적화 작업 결과

### 1. 개요 및 목적
- 지도가 로드되거나 필터가 변경될 때마다 120여 개 마커에 대해 실시간으로 역지오코딩 API(`resolveAddress`)가 작동하여 API 호출량(하루 2만 건 이상)이 과다 청구되던 구조적 결함을 근본적으로 개선했습니다.

### 2. 변경된 내용
- **Supabase DB 마이그레이션 (`add_address_to_markers.sql`)**:
  - `markers` 테이블에 `road_address` 및 `jibun_address` 컬럼을 추가하는 DDL 스크립트를 작성 및 제공했습니다.
- **`data-manager.js` 데이터 보존 지원**:
  - JSON 복원(`importFromJSON`) 시 주소 정보가 깎여 유실되지 않도록 `roadAddress`, `jibunAddress` 속성을 맵핑 객체로 수집하는 로직을 보강했습니다.
  - Excel/CSV 업로드(`parseExcelOrCSV`) 시 엑셀 내 주소 정보가 있으면 이를 `roadAddress`에 미리 채워두도록 업데이트했습니다.
- **`app.js` API 호출 최적화 및 백그라운드 자동 마이그레이션**:
  - **마커 렌더링 최적화**: `createOverlayContent`에서 데이터 객체에 주소 정보(`data.roadAddress`, `data.jibunAddress`)가 이미 있는 경우 Geocoder API 호출을 완전히 생략하고 렌더링하도록 갱신했습니다.
  - **구데이터 백그라운드 마이그레이션 (폴백)**: 기존에 주소가 비어 있던 마커에 대해서만 최초 렌더링 시 API를 1회 호출하며, 호출 완료 시점에 로컬 메모리를 갱신함과 동시에 Supabase DB에 백그라운드로 주소를 자동 업데이트(`update`)하여 향후 재방문 시 호출량이 0이 되도록 마이그레이션 로직을 적용했습니다.
  - **CRUD 및 위치 이동 연동**:
    - 마커 생성/저장(`handleSaveMarker`), 대기 마커 개별 전송(`handleUploadSinglePending`) 및 일괄 전송(`handleUploadPending`) 시, Geocoder를 통해 주소 정보를 받아와 `road_address`, `jibun_address` 컬럼에 실어 DB에 최종 반영하도록 변경했습니다.
    - 마커 드래그 위치 수정 저장(`saveMarkerPosition`) 시에도 새 좌표에 대해 역지오코딩을 1회 재요청하여 변경된 위치의 신규 주소로 DB를 정밀 갱신하도록 구성했습니다.
    - JSON 백업/복원 기능 작동 시에도 주소 필드가 DB 및 파일 양방향으로 완벽하게 연계되도록 처리했습니다.

### 3. 검증 결과
- **호출량 차단 검증**: F12 개발자 도구의 네트워크 탭 분석 결과, 지도를 새로고침하거나 연도/사업구분 필터를 조작하더라도 카카오 Geocoder API(`coord2address`)가 120여 번씩 무분별하게 날아가던 현상이 완벽하게 사라지고 **0건**으로 동작함을 확인했습니다.
- **구데이터 자동 갱신 검증**: 기존에 주소가 비어 있던 마커가 최초 렌더링되며 1회 API를 통해 주소를 구한 뒤, Supabase `markers` 테이블에 `road_address`와 `jibun_address`가 백그라운드로 성공적으로 자동 보정되어 기입되는 것을 확인했습니다.
- **신규 핀 등록 및 위치 변경 주소 보정**: 신규 마커 등록 및 핀 위치 변경 저장 시 Supabase DB에 실시간 변환된 최신 도로명 및 지번 주소가 유실이나 누락 없이 정확하게 기재됨을 검증 완료했습니다.
- **백업 파일 데이터 검증**: 백업받은 JSON 파일을 확인했을 때 `roadAddress` 및 `jibunAddress` 정보가 누락 없이 안정적으로 파일 내에 기재되어 내려받아지고, 이를 통한 복원 역시 문제없이 무결하게 수행됨을 검증했습니다.

## [2026-06-08] 마커 위치 변경 모드 중 오버레이 클릭 시 이벤트 버블링으로 인한 순간이동 버그 수정 결과

- 마커의 위치 변경 모드에서 핀을 임시 이동시킨 후, 오버레이 말풍선 내의 `[저장]` 또는 `[취소]` 버튼을 누르면 마우스 포인터가 가리키는 지도로 핀이 강제 이동(순간이동)된 뒤 저장되는 버그를 수정했습니다.

### 2. 변경된 내용
- **`app.js` 내 커스텀 오버레이 이벤트 전파 방지 적용**:

## [2026-06-06] 마커 상세 및 편집 모드 분리 작업 결과

### 1. 개요 및 목적

### 2. 변경된 내용
- **`app.js` 내 상세/편집 분리 대응**
  - **오버레이 버튼 구성 변경 (`createOverlayContent`)**: [상세] 버튼과 [편집] 버튼을 모두 생성하여 하단 액션바에 추가하고, 클릭 이벤트가 지도 또는 마커로 전달되어 원치 않는 이동이 발생하지 않도록 `e.stopPropagation()` 처리를 추가하였습니다.
  - **폼 읽기 전용 토글 헬퍼 (`toggleModalReadOnly`)**: 장소 이름, 메모, 태그 등의 입력 필드를 대상으로 `readonly` 속성과 `input-readonly` CSS 클래스를 동적으로 제어합니다. 위도와 경도는 원래 설계대로 항상 읽기 전용 상태를 유지합니다.
  - **상세 모달 모드 (`openDetailMarkerModal`)**: 모달 제목을 '마커 상세 정보'로 변경하고 모든 입력 필드를 읽기 전용 상태로 잠급니다. [저장] 및 [삭제] 버튼을 감추고 우측 하단 취소 버튼의 명칭을 '닫기'로 변환합니다.
  - **편집 모달 모드 (`openEditMarkerModal`)**: 모든 입력 필드를 쓰기 가능 상태로 활성화하고, [저장] 버튼을 상시 노출하며 `isPending = true`가 아닌 영구 저장 마커인 경우에만 [삭제] 버튼을 노출합니다.
  - **대기 마커 편집 예외 처리 (`handleSaveMarker`)**: 아직 DB에 저장되지 않은 대기 마커(`isPending = true`)를 수정하여 저장하는 경우, Supabase API를 타지 않고 로컬 메모리상에서만 데이터가 갱신되도록 하였습니다.

### 3. 검증 결과
- **상세 조회**: 오버레이 정보창의 **[상세]** 클릭 시 폼이 비활성화되고 입력이나 수정이 불가능하며 [저장]/[삭제] 버튼이 숨겨지고 오직 [닫기] 버튼만 하단에 렌더링됨을 검증했습니다.
- **정보 편집**: 오버레이 정보창의 **[편집]** 클릭 시 폼이 정상 활성화되고 [저장] 및 [취소] 버튼이 정상 동작하며 수정 정보가 로컬 저장소 및 Supabase에 알맞게 반영됨을 확인했습니다.
